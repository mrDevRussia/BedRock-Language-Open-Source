## Official Language Specification and Reference Manual

**Version:** 1.0  
**Target Architecture:** MIPS32 (Realtek RTL8676S)  
**Compilation Model:** One-pass, deterministic, ahead-of-time  
**Byte Order:** Big-Endian

## Introduction

BedRock is a systems programming language designed for bare-metal embedded systems. It compiles directly to MIPS32 machine code without runtime overhead, virtual machines, or hidden abstractions. Every language construct maps directly to processor instructions, providing complete transparency and deterministic behavior.

### Design Goals

- **No Magic:** Every statement translates to explicit machine instructions
- **Byte-Level Control:** Programmers control exact memory layout and execution order
- **Deterministic Compilation:** Source code order equals binary code order (one-pass compilation)
- **Zero Runtime:** No garbage collection, no dynamic dispatch, no hidden allocations
- **Hardware Direct:** Memory-mapped I/O is a first-class language feature

### Target Use Cases

- Medical embedded systems
- Real-time control systems
- Bootloaders and firmware
- Hardware device drivers
- Systems requiring deterministic timing

---

## Philosophy

### The "No Plastic Code" Principle

Traditional high-level languages introduce layers of abstraction that obscure the underlying hardware behavior. BedRock rejects this approach. In BedRock:

- There are no hidden function calls
- No implicit memory allocations
- No automatic type conversions
- No compiler optimizations that reorder code
- No runtime libraries required

### Transparency Over Convenience

BedRock prioritizes transparency and predictability over programmer convenience. When you write:

```bedrock
poke(0xB80003F8, 65);
```

The compiler generates exactly two MIPS instructions:
1. Load immediate value 65 into a register
2. Store byte to address 0xB80003F8

Nothing more, nothing less.

### Deterministic Execution Model

The BedRock compiler uses a **one-pass compilation model**:

1. Source file is read sequentially
2. Code is generated in the exact order it appears
3. Binary layout matches source layout
4. No optimization passes reorder instructions

This guarantees that:
- Execution timing is predictable
- Hardware initialization sequences execute in correct order
- Memory-mapped I/O operations happen exactly when specified

## Language Overview

### File Extension

BedRock source files use the `.br` extension.

### Character Set

BedRock source files are encoded in UTF-8. Only ASCII characters are significant in the language syntax.

### Comments

BedRock currently does not support comments in the language syntax. Documentation is maintained in separate files.

### Program Structure

A BedRock program consists of:

1. **Root declarations** (hardware address definitions)
2. **Global variable declarations**
3. **Function definitions**
4. **Global code** (executed at program start)

Example:

```bedrock
root UART_BASE = 0xB80003F8;

let counter = 0;

fn increment() {
    counter = counter + 1;
}

counter = 10;
increment();
loop {}
```

## Lexical Structure

### Keywords

BedRock defines the following reserved keywords:

| Keyword | Purpose |
|---------|---------|
| `fn` | Function definition |
| `let` | Variable declaration |
| `root` | Hardware address constant |
| `if` | Conditional statement |
| `else` | Alternative conditional branch |
| `while` | Conditional loop |
| `loop` | Infinite loop |
| `break` | Exit loop |
| `return` | Exit function |
| `poke` | Write to memory address |
| `peek` | Read from memory address |
| `outb` | Write byte to I/O port (alias for poke) |
| `inb` | Read byte from I/O port |
| `asm` | Inline assembly (reserved) |
| `include` | Include another source file |

### Identifiers

Identifiers must:
- Start with a letter (a-z, A-Z) or underscore (_)
- Contain only letters, digits (0-9), and underscores
- Not be a reserved keyword

Valid identifiers:
```
myVariable
_private
counter_1
GPIO_PIN_2
```

Invalid identifiers:
```
123abc      // starts with digit
my-var      // contains hyphen
if          // reserved keyword
```

### Literals

#### Integer Literals

Decimal:
```bedrock
let x = 42;
let y = 1000;
```

Hexadecimal (0x prefix):
```bedrock
let addr = 0xB80003F8;
let mask = 0xFF;
```

#### String Literals

Double-quoted strings:
```bedrock
let msg = "Hello World";
```

String literals are automatically converted to byte arrays.

### Operators

| Operator | Description | Example |
|----------|-------------|---------|
| `=` | Assignment | `x = 5;` |
| `+` | Addition | `a + b` |
| `-` | Subtraction | `a - b` |
| `*` | Multiplication | `a * b` |
| `/` | Division | `a / b` |
| `==` | Equality comparison | `a == b` |
| `<` | Less than | `a < b` |
| `>` | Greater than | `a > b` |

### Delimiters

| Symbol | Purpose |
|--------|---------|
| `(` `)` | Function calls, expressions |
| `{` `}` | Code blocks |
| `[` `]` | Array literals, indexing |
| `;` | Statement terminator |
| `,` | Separator |

## Data Types

BedRock has a minimalist type system focused on hardware representation.

### Integer Type

All numeric values are **unsigned 64-bit integers** during compilation, but are stored as **32-bit words** in the compiled binary (MIPS32).

```bedrock
let x = 42;           // Stored as 32-bit word
let addr = 0x80000000; // 32-bit address
```

### Arrays

Fixed-size arrays of integers:

```bedrock
let data = [1, 2, 3, 4, 5];
let first = data[0];
let last = data[4];
```

Arrays are allocated at fixed memory addresses determined during compilation.

### Strings

Strings are arrays of bytes (ASCII):

```bedrock
let message = "Hello";
```

Equivalent to:
```bedrock
let message = [72, 101, 108, 108, 111];
```

### No Other Types

BedRock intentionally does not support:
- Floating-point numbers
- Structures/records
- Pointers (addresses are integers)
- Booleans (use 0 and 1)

## Statements

### Variable Declaration

Syntax:
```bedrock
let identifier = expression;
```

Example:
```bedrock
let count = 0;
let max = 100;
let sum = count + max;
```

Variables are allocated at fixed memory addresses.

### Assignment

Syntax:
```bedrock
identifier = expression;
```

Example:
```bedrock
count = 5;
count = count + 1;
```

### Root Declaration

Defines a constant hardware address or configuration value:

Syntax:
```bedrock
root identifier = expression;
```

Example:
```bedrock
root UART_BASE = 0xB80003F8;
root GPIO_PORT = 0xB8003500;
```

Root values cannot be changed after declaration. They exist only during compilation and do not consume runtime memory.

### If Statement

Syntax:
```bedrock
if condition {
    statements
}

if condition {
    statements
} else {
    statements
}
```

Example:
```bedrock
if x > 10 {
    y = 1;
}

if status == 0 {
    poke(LED_ADDR, 1);
} else {
    poke(LED_ADDR, 0);
}
```

### While Loop

Syntax:
```bedrock
while condition {
    statements
}
```

Example:
```bedrock
let i = 0;
while i < 10 {
    poke(UART_BASE, 65);
    i = i + 1;
}
```

### Infinite Loop

Syntax:
```bedrock
loop {
    statements
}
```

Example:
```bedrock
loop {
    let sensor = peek(ADC_CHANNEL);
    poke(DISPLAY, sensor);
}
```

### Break Statement

Exits the innermost loop:

```bedrock
let i = 0;
loop {
    if i == 10 {
        break;
    }
    i = i + 1;
}
```

### Memory Operations

#### poke - Write to Memory

Syntax:
```bedrock
poke(address, value);
```

Writes a single byte to the specified memory address.

Example:
```bedrock
poke(0xB80003F8, 65);  // Write 'A' to UART
poke(GPIO_DATA, 1);     // Set GPIO pin high
```

Compiled to: `sb` (store byte) instruction

#### peek - Read from Memory

Syntax:
```bedrock
peek(address)
```

Reads a single byte from the specified memory address.

Example:
```bedrock
let status = peek(UART_STATUS);
if status == 1 {
    poke(UART_BASE, 42);
}
```

Compiled to: `lb` (load byte) instruction

### Function Call

Syntax:
```bedrock
function_name(arguments);
```

Example:
```bedrock
print_char(65);
delay(1000);
calculate(x, y);
```

### Return Statement

Exits the current function:

```bedrock
fn get_value() {
    return;
}
```

Note: BedRock currently does not support return values. Functions communicate through global variables or memory-mapped I/O.

## Expressions

### Primary Expressions

#### Literals

```bedrock
42          // Integer literal
0xFF        // Hexadecimal literal
```

#### Variables

```bedrock
counter
my_variable
GPIO_PIN_3
```

#### Array Access

```bedrock
data[0]
sensors[index]
message[i]
```

### Binary Operations

#### Arithmetic

```bedrock
a + b       // Addition
a - b       // Subtraction
a * b       // Multiplication
a / b       // Division
```

#### Comparison

```bedrock
a == b      // Equality
a < b       // Less than
a > b       // Greater than
```

Comparison operators return:
- 1 if true
- 0 if false

### Operator Precedence

BedRock uses left-to-right evaluation without precedence:

```bedrock
let result = 2 + 3 * 4;  // Evaluated as (2 + 3) * 4 = 20
```

Use parentheses for different grouping (not currently supported - evaluate manually):

```bedrock
let x = 2 + 3;
let result = x * 4;  // Explicit ordering
```

## Functions

### Function Definition

Syntax:
```bedrock
fn name(parameter1, parameter2, ...) {
    statements
}
```

Example:
```bedrock
fn add(a, b) {
    sum = a + b;
}

fn print_char(c) {
    poke(UART_BASE, c);
}

fn delay(count) {
    let i = 0;
    while i < count {
        i = i + 1;
    }
}
```

### Parameters

Function parameters are passed by value. They are accessible as local variables within the function scope.

```bedrock
fn multiply(x, y) {
    result = x * y;
}
```

### No Return Values

BedRock functions do not return values directly. Instead:

1. Use global variables:
```bedrock
let result = 0;

fn calculate(x) {
    result = x * 2;
}

calculate(5);
// result now contains 10
```

2. Use memory-mapped locations:
```bedrock
fn read_sensor(sensor_addr, output_addr) {
    let value = peek(sensor_addr);
    poke(output_addr, value);
}
```

### Calling Convention

Functions are compiled with standard MIPS calling convention:
- Parameters passed on stack
- Return address saved in `$ra`
- Stack frame allocated/deallocated automatically

## Memory Model

### Memory Layout

BedRock programs execute in a flat 32-bit address space:

```
0x00000000 - 0x7FFFFFFF : Unmapped
0x80000000 - 0x800FFFFF : Code and Data (RAM)
0x80100000 - 0x801FFFFF : Stack
0xB8000000 - 0xBFFFFFFF : Memory-mapped I/O
```

### Variable Storage

Variables are allocated at fixed addresses determined during compilation:

```bedrock
let var1 = 10;  // Allocated at 0x80001000
let var2 = 20;  // Allocated at 0x80001004
```

Each variable occupies 4 bytes (32-bit word).

### Array Storage

Arrays are stored as contiguous words:

```bedrock
let data = [1, 2, 3, 4];
// Stored as:
// 0x80001000: 0x00000001
// 0x80001004: 0x00000002
// 0x80001008: 0x00000003
// 0x8000100C: 0x00000004
```

### String Storage

Strings are stored as byte arrays:

```bedrock
let msg = "Hi";
// Stored as:
// 0x80001000: 0x48 ('H')
// 0x80001001: 0x69 ('i')
// 0x80001002: 0x00 (padding)
// 0x80001003: 0x00 (padding)
```

Strings are aligned to 4-byte boundaries.

### Memory-Mapped I/O

Hardware devices are accessed through memory addresses:

```bedrock
root UART_BASE = 0xB80003F8;
root GPIO_BASE = 0xB8003500;

poke(UART_BASE, 65);      // Write to UART
let status = peek(GPIO_BASE); // Read GPIO
```

## Standard Library

BedRock intentionally has no built-in standard library. All functionality is implemented in user code or library files.

### Recommended Library Structure

```
stdlib/
  core/
    io.br          - UART, console I/O
    memory.br      - Memory utilities
    math.br        - Arithmetic operations
  hardware/
    uart.br        - UART driver
    gpio.br        - GPIO control
    i2c.br         - I2C communication
  system/
    types.br       - Common type definitions
```

### Include Mechanism

Use `include` to incorporate library code:

```bedrock
include "stdlib/core/io.br";

print_char(65);
```

The preprocessor includes files before compilation, similar to C's `#include`.

## Examples

### Example 1: Hello World

```bedrock
root UART_BASE = 0xB80003F8;

let msg = [72, 101, 108, 108, 111];  // "Hello"
let i = 0;

while i < 5 {
    let ch = msg[i];
    poke(UART_BASE, ch);
    i = i + 1;
}

loop {}
```

### Example 2: GPIO LED Blink

```bedrock
root GPIO_DATA = 0xB8003508;
root LED_PIN = 0x01;

fn delay(count) {
    let i = 0;
    while i < count {
        i = i + 1;
    }
}

loop {
    poke(GPIO_DATA, LED_PIN);
    delay(100000);
    poke(GPIO_DATA, 0);
    delay(100000);
}
```

### Example 3: I2C LCD Driver

```bedrock
include "config/realtek_roots.br";

root I2C_DATA = 0xB8003000;
root I2C_CTRL = 0xB8003004;
root I2C_STATUS = 0xB8003008;
root LCD_ADDR = 0x27;

fn i2c_start() {
    poke(I2C_CTRL, 0x01);
}

fn i2c_stop() {
    poke(I2C_CTRL, 0x02);
}

fn i2c_write(data) {
    poke(I2C_DATA, data);
    poke(I2C_CTRL, 0x04);
    
    let status = 0;
    while status == 0 {
        status = peek(I2C_STATUS);
    }
}

fn lcd_write_char(c) {
    i2c_start();
    i2c_write(LCD_ADDR);
    i2c_write(c);
    i2c_stop();
}

lcd_write_char(65);
loop {}
```

### Example 4: Pulse Sensor Monitor

```bedrock
root ADC_CHANNEL = 0xB8004000;
root ADC_CTRL = 0xB8004010;
root UART_BASE = 0xB80003F8;

fn read_adc() {
    poke(ADC_CTRL, 0x01);
    
    let status = 0;
    while status == 0 {
        status = peek(ADC_CTRL);
        status = status & 0x02;
    }
    
    let value = peek(ADC_CHANNEL);
    return value;
}

fn print_value(val) {
    // Simple byte output
    poke(UART_BASE, val);
}

loop {
    let pulse = read_adc();
    print_value(pulse);
}
```

## Compiler Implementation

### Compilation Phases

The BedRock compiler executes in strict sequential order:

#### Phase 1: Bootstrap
- Generate processor initialization code
- Set up stack pointer
- Disable interrupts

#### Phase 2: Root Collection
- Parse all `root` declarations
- Build symbol table of constants

#### Phase 3: Static Data Allocation
- Allocate memory for arrays and strings
- Determine fixed addresses

#### Phase 4: Function Code Generation
- Generate machine code for all functions
- Record function entry points

#### Phase 5: Static Data Initialization
- Generate code to write array/string data to memory
- Execute before global code

#### Phase 6: Global Code Generation
- Generate code for statements outside functions
- This code executes at program start

#### Phase 7: Halt
- Generate infinite loop (program end)

### Code Generation

BedRock generates native MIPS32 instructions:

| BedRock | MIPS Assembly |
|---------|---------------|
| `let x = 5;` | `li $t0, 5` <br> `sw $t0, addr` |
| `poke(addr, val);` | `li $t0, val` <br> `li $t1, addr` <br> `sb $t0, 0($t1)` |
| `x = x + 1;` | `lw $t0, addr` <br> `addiu $t0, $t0, 1` <br> `sw $t0, addr` |
| `while x < 10` | `loop:` <br> `lw $t0, addr` <br> `slti $t1, $t0, 10` <br> `beq $t1, $zero, end` <br> `...` <br> `j loop` <br> `end:` |

### Binary Format

Output is raw MIPS32 machine code:
- Big-endian byte order
- 32-bit instructions (4 bytes each)
- No executable headers (bare metal)

### Memory Allocation Strategy

Variables and arrays are allocated sequentially starting at `0x80001000`:

```
0x80000000 - 0x80000FFF : Code
0x80001000 - 0x8000FFFF : Data
0x80010000 - 0x800FFFFF : Free
0x80100000 - ...        : Stack
```

## Limitations and Design Decisions

### No Dynamic Memory

BedRock does not support:
- `malloc`/`free`
- Dynamic arrays
- Heap allocation

All memory must be statically allocated.

### No Recursion Support

While syntactically possible, deep recursion may overflow the stack. Iterative solutions are preferred.

### No Function Return Values

Functions communicate through:
- Global variables
- Memory-mapped I/O
- Parameters (modified in place)

### No Type System

All values are 32-bit integers. Type safety is the programmer's responsibility.

### No Standard I/O

There is no `printf` or `scanf`. All I/O must be explicitly programmed using `poke`/`peek`.

## Language Grammar (EBNF)

```ebnf
program = { statement } ;

statement = let_stmt
          | root_stmt
          | assignment
          | if_stmt
          | while_stmt
          | loop_stmt
          | break_stmt
          | return_stmt
          | poke_stmt
          | fn_def
          | fn_call ;

let_stmt = "let" identifier "=" expression ";" ;
root_stmt = "root" identifier "=" expression ";" ;
assignment = identifier "=" expression ";" ;
if_stmt = "if" expression "{" { statement } "}" [ "else" "{" { statement } "}" ] ;
while_stmt = "while" expression "{" { statement } "}" ;
loop_stmt = "loop" "{" { statement } "}" ;
break_stmt = "break" ";" ;
return_stmt = "return" ";" ;
poke_stmt = "poke" "(" expression "," expression ")" ";" ;
fn_def = "fn" identifier "(" [ param_list ] ")" "{" { statement } "}" ;
fn_call = identifier "(" [ arg_list ] ")" ";" ;

expression = primary { binary_op primary } ;
primary = number
        | identifier
        | array_access
        | "peek" "(" expression ")" ;

array_access = identifier "[" expression "]" ;
binary_op = "+" | "-" | "*" | "/" | "==" | "<" | ">" ;
param_list = identifier { "," identifier } ;
arg_list = expression { "," expression } ;
```

## Conclusion

BedRock is a minimalist systems language for programmers who need complete control over hardware. It sacrifices convenience for transparency, predictability for flexibility, and abstraction for directness.

BedRock is not for everyone. It is for:
- Embedded systems programmers
- Hardware engineers
- Students learning computer architecture
- Anyone building systems from the ground up

If you need a garbage collector, object orientation, or extensive standard libraries, BedRock is not the right choice. But if you need to know **exactly** what your processor is doing at every clock cycle, BedRock gives you that power.
